## Назначение и состав

Эталонные конфигурации без секретов для шагов 3–6 развёртывания.
Основа — комплект Claude:
[описание комплекта](../project-stages/01-make-stand/result-01-stand-config.md).
При различиях настройки в infrastructure/ описывают текущий вариант рабочего стенда;
документ Claude остаётся исходным предложением.

- postgres/compose.yaml — учебная PostgreSQL 17, проект postgres.
- postgres/.env.example — шаблон её локальных настроек.
- superset/compose.avalon.yaml — дополнение к штатному Compose Superset 3.1.1.
- superset/.env.example — шаблон настроек Superset.

Docker Engine 29.9.2 и Compose 5.6.1 установлены пользователем;
работа через sudo, группы не менялись. Для !override нужен Compose >= 2.24.4.
Пользователь запустил сервисы на рабочей ВМ: учебная БД 17.11 healthy,
init Superset завершён с кодом 0; веб и зависимости работают.
Проверены вход и права чтения на синтетической таблице.
Внутри веб-контейнера /health — HTTP 200, но доступ с хоста заблокирован.
[Актуальный статус](../docs/status.md) и
[диагностика](../project-stages/01-make-stand/incident-01-superset-access.md).
Стенд пока не прошёл полную приёмку.

## Размещение файлов запуска

Репозиторий Avalon хранит эталонные файлы. Запуск выполняется отдельно:

```text
~/bi-stand/
├── postgres/
│   ├── compose.yaml
│   └── .env
└── superset/                       # checkout apache/superset, tag 3.1.1
    ├── docker-compose-non-dev.yml   # штатный, без правки строки образа
    ├── compose.avalon.yaml
    ├── .env
    └── docker/                     # обязательные скрипты и конфигурации upstream
```

Не копировать только штатный Compose: его относительные зависимости
должны остаться в checkout Superset. Вложенный checkout Superset
не размещать внутри Git-репозитория Avalon.
После получения тега записать commit в описание рабочего стенда.

Фактические данные — named volumes postgres_study_data,
superset_db_home, superset_superset_home, superset_redis.
Переносить Docker data-root и создавать /data для этого варианта не требуется.
Имена проектов закреплены, смена каталога не меняет их автоматически.

## Секреты и локальные настройки: шаг 4

Пользователь копирует шаблоны в runtime .env, задаёт свои значения
и права 600. Настоящие .env агент не читает, в Git они не попадают.
Заглушки <...> нельзя использовать как действующие значения.

Для паролей подходит локальная генерация openssl rand -hex 24,
для ключа Superset — openssl rand -base64 42.
Не присылать результаты агенту. Ключ задать до первого запуска
и сохранить для восстановления отдельно от Git.
Изменение POSTGRES_PASSWORD в .env не меняет пароль уже созданного кластера.

Верхнеуровневый .env Superset используется Compose для подстановок
и выбора двух файлов. Штатный docker/.env-non-dev — источник базовых
переменных контейнеров; environment из override заменяет его секреты.
EXAMPLES_PASSWORD задаётся и при выключенной загрузке примеров:
upstream создаёт базу examples при инициализации служебного PostgreSQL.

Стандартный администратор upstream должен получить новый пароль
пользователем сразу после инициализации. До этого порт остаётся
привязан к loopback; службы БД и Redis Superset наружу не публикуются.

## Изменения относительно предложения Claude

- Образ apache/superset:3.1.1 задан для всех четырёх сервисов
  в override; sed-правку upstream Compose выполнять не нужно.
- PostgreSQL и Redis имеют healthcheck; init ждёт их готовности,
  веб и workers дополнительно ждут успешного завершения init.
- Имена обоих Compose-проектов закреплены явно.
- Учётные данные служебной БД передаются только нужным сервисам.
- pg_isready проверяет приём соединений, а не корректность пароля
  и прав приложения: подключение проверяется отдельно.
- depends_on управляет порядком запуска через Compose, но не
  гарантирует порядок старта при перезагрузке Docker. После
  перезагрузки нужно проверить здоровье всех сервисов.

## Порядок воспроизведения и проверки

Ниже — порядок первоначального развёртывания, а не предложение
повторно создавать уже существующие объекты.
Команды выполняются в runtime-каталогах после подготовки файлов и секретов.
Текущее выполнение см. в docs/status.md.

1. Один раз создать общую внешнюю сеть bi-net.
2. В каталоге postgres проверить конфигурацию:
   sudo docker compose config --quiet
3. Запустить учебную базу:
   sudo docker compose up -d --wait
4. Создать роль чтения под административной ролью в интерактивном psql:
   сначала CREATE ROLE superset_ro LOGIN; затем команда
   `\password superset_ro` для скрытого ввода пароля.
   Не вставлять пароль в CREATE ROLE ... PASSWORD.
5. Выдать CONNECT на study, USAGE на public, SELECT на текущие таблицы.
   ALTER DEFAULT PRIVILEGES выполнять для роли, которая будет создавать
   будущие таблицы, а не произвольного текущего пользователя.
6. В runtime checkout Superset проверить конфигурацию:
   sudo docker compose config --quiet
7. Запустить Superset: sudo docker compose up -d --wait --wait-timeout 300.
   При ошибке init не удалять volumes; сначала разобрать причину.
8. Проверить завершение init с кодом 0, здоровье веба и workers,
   доступ через SSH-туннель и подключение к bi-postgres:5432/study.
9. На синтетической таблице проверить график и права чтения.
10. Перезапуск сервисов и перезагрузка ВМ — отдельная согласованная
    проверка с контролем сохранности данных и настроек.

Полный docker compose config, docker inspect, env и необработанные
журналы могут раскрыть секреты. Предпочитать config --quiet
и выборочные безопасные проверки.
Привязки 127.0.0.1:5432 и 127.0.0.1:8088 не предоставляют
руководству прямой сетевой доступ: он настраивается отдельно.

## Сетевая совместимость рабочей ВМ

UFW и KESL влияют на доступ хоста к Docker-сервисам.
Временное узкое исключение UFW не решило проблему.
Не переносить его автоматически на другие стенды и не отключать
защиту для проверки. Устойчивое решение согласует администратор ВМ/KESL.
Настройки корпоративной защиты не включены в общую конфигурацию Compose.

## Ограничения

- postgres:17, postgres:15 и redis:7 — плавающие теги.
  После скачивания записать версии и digest фактических образов.
  Точное совпадение с домашними образами пока не подтверждено.
- Superset 3.1.1 сохранён по исходному комплекту; это версия для
  согласованного MVP. Обновление версии — отдельная задача.
- Проверка Compose не доказывает работоспособность контейнеров.
- Резервное копирование и пробное восстановление нужно подготовить
  до постоянной работы с корпоративными данными.

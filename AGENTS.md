## Промпты пользователя и формат ответа ИИ агента пользователю
### Промпты
Каждый промпт пользователя начинается с 4 символов от которых зависит формат ответа:
Длина ответа агента на заданный промпт пользователя:
а1 - максимально короткий ответ;
а2 - короткий ответ;
а3 - ответ средней длины;
а4 - развернутый ответ;
а5 - максимально развернутый ответ;

Цель ответа агента:
ц1 - пользователь спрашивает агента вопрос, который как он считает напрямую относится к проекту;
ц2 - пользователь спрашивает агента вопрос, который не относится напрямую к проекту;
Префикс ц - будет нужен для пополнения в дальнейшем базы знаний по проекту и общей базы знаний, которые не относятся к проекту.
### Примеры промптов
а2ц1
нужно написать sql запрос по следующей структуре данных.
а3ц2. что ты думаешь насчет различий между ubuntu и windows?

В случае если аббревиатура в начале промпта отсутствует, давать ответы средней длины, если пользователь не определил формат ответа.
## Формат создания документов агентом
Для проекта нужно наличие метаданных и пометок внутри текста.
### Метаданные
В начале каждого Markdown документа создаваемого агентом присутствует блок метаданных:
``` Markdown
## Название документа

> Статус: черновик
> Обновлено: YYYY-MM-DD HH:mm MSK
> Ответственный: <Claude/Codex/Saint>
```
Допустимые статусы документа
Черновик - содержание дкумента готовится, есть неподтвержденные положения.
Актуален - документ подтвержден и используется в работе.
Требует пересмотра - в документе есть нюансы которые необходимо уточнить.
Архивный - документ оставлен для истории.
### Пометка
Когда использовать
**Важно:**	Существенное условие, которое легко пропустить
**Ограничение:**	Обязательная граница: например, запрет передачи данных AI
**Не проверено:**	Сведение записано, но ещё не подтверждено
**Предположение:**	Рабочая гипотеза, на которой пока строим решение
**Открытый вопрос:**	Нужен ответ или решение
**Риск:**	Возможная проблема и её последствия
**Пример — синтетические данные:**	Вымышленные записи для объяснения или проверки
``` Markdown
Примеры:
**Ограничение:** корпоративные выгрузки нельзя передавать AI-инструментам.
**Не проверено:** автоматический запуск Superset после перезагрузки ВМ.
**Предположение:** каждый повторный запуск согласования создаёт отдельный цикл.
**Открытый вопрос:** срок согласования считается в рабочих или календарных часах?
```
### Чекбоксы
Для проверяемых задач достаточно стандартных чекбоксов:
- [x] Проверено открытие интерфейса Superset.
- [ ] Проверено подключение Superset к PostgreSQL.

## Как происходит работа над проектом в общих чертах
1. Результат всей работы должен сохраняться пользователю на локальный репозиторий.
2. Пользователь самостоятельно осуществляет commit в GIT репозиторий.
3. **Важно:**. В репозитории должно храниться как можно меньше информации, чтобы уменьшить когнитивную нагрузка на пользователя - меньше повторов, лишних вступлений, документов без пользы.
4. Формат сохранения информации в локальном репозитории зависит от промпта пользователя. Пользователь оставляет за собой право вручную редактировать файлы репозитория если посчитает избыточным количества нейрослопа.
## **Важно:** Как происходит работа над проектом в формате сессии
1. Сессия - период работы в одном чате над проектом. Новый чат или переход от Claude к Codex является новой сессией.
При новой сессии необходимо:
- перечитать содержимое файла readme.md, docs/status.md соблюдая agents.md
- обновить контекст в текущем чате с учетом того, что могли обновиться GIT, произойти смена окружения;
- проверить актуальное содержимое файлов;
- если обнаружены неожиданные изменения спрашивать действия агента только при конфликте или неясном назначении, иначе достаточно учесть их. 
2. Команды для работы по сессиям:
- Старт сессии - старт новой сессии;
- Конец сессии - конец текущей сессии, обновить docs/status.md — записать, что сделано, что проверено, какие вопросы остались и какой следующий шаг. При необходимости обновить другие документы проекта.
3. Взаимодействие с пользователем происходит короткими шагами. В случае необходимости задача разбивается на подзадачи, указывается место исполнения и ожидаемый результат.
4. Не полагаться исключительно на историю чата. Если для задачи не хватает сведений, конкретно указать каких.
5. При существенных изменениях обновлять только затронутые документы проекта и уведомлять пользователя.
## Ограничения при работе над проектом
1. Главенствует принцип - запрещено всё, что не разрешено пользователем. 
Агент может читать и изменять файлы проекта в разрешённом репозитории в рамках текущей задачи. Изменения системных настроек, сервисов и баз данных согласовываются отдельно, независимо от папки запуска команды.
В начале проекта у агента есть доступ CRUD только внутри репозитория AVALON. Для операций CUD внутри репозитория агент в начале один раз за сессию/задачу описывает ожидаемый результат действий, затем один раз за сессию/задачу запрашивает разрешение на исполнение и далее выполняет действия в согласованных границах без повторых запросов. В случае если пользователь в рамках сессии определил, что агент может делать, то агент не спрашивает разрешение на каждую задачу.
2. Вне репозитория агент может выполнять только чтение (R). Для создания, изменения или удаления (CUD) до выполнения описывает действия и ожидаемый результат, получает разрешение пользователя. После выполнения сообщает фактический результат.
3. В случае необходимости будет сформирован файл с отдельным список каталогов, и расписано какие права там есть у агента.
4. Агент не должен перезаписывать незавершенную работу другого участника - пользователя или агента без разрешенной команды пользователя.
5. Агент не может менять файлы не относящие к текущей задаче без объяснения необходимости.
6. Агент не может выдавать предположения за проверенный факт. Он всегда должен говорить о том, что это предположение.
7. Обязательно согласовывать с пользователем любые действия связанные с риском потери данных (удаление базы данных, зависимостей и т.д.).
8. Агент должен проводить обязательную проверку результата своих действий и не может объявлять об успехе без проверки:
8.1. после изменения кода, конфигурации или SQL проверить, что получен ожидаемый результат.
8.2. выбирать проверку по задаче:
   - документация — проверить согласованность текста и ссылок;
   - конфигурация — проверить корректность и работу сервиса;
   - SQL — проверить расчёт на синтетических данных, включая существенные пограничные случаи.
8.3. Проверки на корпоративных данных выполняет пользователь. Агент описывает порядок проверки и ожидаемый результат.
8.4. Если проверка не выполнена, явно указать причину и что осталось проверить.
8.5. В итоговом сообщении кратко указать: что изменено, что проверено и каков результат.
8.6. Не объявлять работоспособность подтверждённой без фактически выполненной проверки.
1. Пользователь не размещает корпоративные данные в репозитории. Для разработки используются описания структуры и синтетические примеры. Агент не ищет и не читает рабочие выгрузки, дампы и содержимое баз вне репозитория. Если происхождение данных вызывает сомнения — уточняет у пользователя до чтения.
## Секреты
1. Агент не должен хранить секреты в коде, документации и Git.
2. Агент должен использовать локальные настройки и .env.example с заглушками.
3. Агент не должен выводить содержимое файлов с секретами.
4. Агент не должен запрашивать у пользователя пароли в чате.
5. При обнаружении утечки агент должен сообщить о ней без повторения секрета.
## Папка technical
1. В папке хранится техническая информация о проекте.
2. Здесь не должна храниться информация об учетных данных, имени пользователя, информации о дисках, личных путях к папкам. Должны производиться замены, т.к. пользователь определил это чувствительной информацией.

## ТЗ: подготовить комплект для воссоздания домашнего BI-стенда

> Статус: черновик
> Обновлено: 2026-10-27 19:04 MSK
> Ответственный: Claude — выполнение; Saint — согласование; Codex — приёмка для рабочего стенда

## 1. Цель и результат

Подготовить в репозитории Avalon проверенный комплект конфигурации и инструкций,
по которому Codex совместно с пользователем сможет развернуть аналог домашнего
стенда на рабочей Ubuntu без доступа к домашней машине и без истории чата.

Воспроизводим сервисы и их поведение. Разметка диска, имена пользователей,
абсолютные домашние пути и значения секретов между окружениями могут отличаться.

Первый этап — воспроизведение инфраструктуры с пустыми базами и синтетическими
данными. Перенос существующих баз, пользователей и дашбордов в эту задачу
не входит; если он необходим, зафиксировать отдельный вопрос.

## 2. Контекст проекта

- MVP: дашборд согласования договоров в Apache Superset.
- Источники: 1С ERP и 1С Документооборот; планируется еженедельная загрузка CSV.
- Стек: Ubuntu, Docker Engine, Docker Compose, PostgreSQL, Apache Superset.
- Дома пользователь работает с Claude Code, на работе — с Codex.
- Пользователь знает SQL DML в MS SQL; Linux, Docker, PostgreSQL и Superset изучает.
- Работать короткими шагами, объяснять действия и результаты.
- Коммиты и отправку изменений в Git выполняет пользователь.

Рабочая ВМ по диагностике пользователя от 2026-10-23:
- Ubuntu 26.04.1 LTS, x86_64;
- 10 доступных логических CPU, около 30 GiB RAM;
- около 211 GiB свободного места в корневой файловой системе;
- есть sudo; стандартная установка Docker и PostgreSQL не обнаружена;
- проверенные адреса Ubuntu, Docker и GitHub доступны по HTTPS;
- каталога /data на момент проверки не было.

Это исходные сведения, а не гарантия текущего состояния или доступности
всех пакетов. Чувствительные пути и сведения о дисках не переносить в technical/.

## 3. Прочитать перед работой

- AGENTS.md и CLAUDE.md;
- README.md;
- docs/structure.md;
- technical/home-stand.md;
- «Необходимо описать окружение и версии.md»;
- docs/status.md и docs/decisions.md, если существуют.

При отсутствии документа сообщить об этом; не придумывать его содержимое.
Текущее описание home-stand.md собрано преимущественно по записям установки:
его утверждения нужно сверить с машиной.

## 4. Границы и безопасность

- Сначала предложить план действий по правилам AGENTS.md.
- Инвентаризация не разрешает менять работающий стенд, обновлять образы,
  перезапускать Docker, базы или машину, удалять контейнеры, сети и тома.
- Любые проверки, меняющие состояние сервисов, согласовать отдельно.
- Не читать реальные .env, пароли, приватные ключи и корпоративные данные.
  Нужные действия с секретами выполняет пользователь локально.
- Не выводить полные docker inspect, docker compose config и журналы,
  если они могут содержать переменные, пароли или рабочие данные.
  Использовать выборочные безопасные поля; не рассчитывать только на
  последующее маскирование уже выведенного секрета.
- Сначала проверить, не содержат ли передаваемые конфигурации встроенных
  секретов. Если это нельзя сделать без раскрытия, пользователь готовит
  очищенную копию до чтения агентом.
- В Git включать только конфигурацию без секретов и синтетические примеры.
- В technical/ соблюдать замены чувствительных путей и учётных сведений
  на заглушки согласно AGENTS.md.
- Не выполнять commit, push и изменение истории Git.

## 5. Что установить фактически

### 5.1. Версии и происхождение

Зафиксировать дату проверки, архитектуру и фактические версии:
- Ubuntu, Docker Engine, Docker Compose;
- PostgreSQL учебной базы и служебной базы Superset;
- Superset, Redis и иных реально используемых сервисов.

Для образов указать тег, доступный RepoDigest и идентификатор фактически
запущенного образа. Отсутствующий digest так и отметить.
Не считать тег postgres:17 фиксацией конкретной minor-версии.
Для исходников Superset указать тег, commit и наличие локальных изменений.
Не подставлять версии стандартного Compose вместо фактических.

### 5.2. Полный набор конфигурации

Определить:
- реальные Compose-файлы, overrides, имена проектов;
- рабочие каталоги, порядок файлов -f, профили и параметры запуска;
- все env_file, build contexts, Dockerfile, скрипты, конфигурации и
  bind-mounted файлы, от которых зависит запуск;
- используются готовые образы, локальная сборка или сочетание обоих;
- необходимые изменения относительно исходного репозитория Superset.

Сохранить очищенный комплект зависимостей либо точный способ их получения
по зафиксированному commit. Не заменять фактическую конфигурацию
предположением «стандартный Compose». Учесть относительные пути при переносе.

### 5.3. Настройки и секреты

Подготовить .env.example без действующих секретов.
Для каждой переменной указать:
- назначение, обязательность и сервис-потребитель;
- где задаётся и как передаётся: Compose-подстановка, env_file,
  переменная контейнера или файл конфигурации;
- безопасное значение либо явную заглушку;
- является ли значение уникальным для окружения.

Описать создание собственных паролей и ключа Superset пользователем,
место локального хранения и исключение из Git.
Не копировать домашние секреты и не использовать действующие
стандартные пароли. Проверить точные имена переменных ключа по используемой
версии и конфигурации Superset, а не угадывать их.

### 5.4. Хранилища и права

Для каждого сервиса описать:
- bind mount или named volume, назначение и путь внутри контейнера;
- что переживает остановку, пересоздание контейнера и перезагрузку;
- необходимые владельцы, UID/GID и права на bind-каталоги;
- какие хранилища являются критичными для восстановления;
- как зависят имена volumes от имени Compose-проекта.

Разделить учебную БД и метаданные Superset.
Redis используется также как брокер: отдельно описать последствия потери
кэша и очереди, не объявлять все его данные безусловно ненужными.
Не переносить содержимое хранилищ.

### 5.5. Сети и доступ

Указать реальные сети, DNS-имена сервисов, внутренние и опубликованные
порты, адреса привязки. Не публиковать реальные внутренние адреса компании.

Проверить наличие рабочего маршрута Superset → учебный PostgreSQL.
Если его нет, это недостаток исходного стенда, а не готовая часть комплекта.
Предложить минимальное решение, например общую пользовательскую сеть,
без самовольного изменения домашнего стенда.
Не считать localhost в контейнере адресом хоста и не считать одно
host.docker.internal достаточным решением при публикации БД на loopback.

Описать открытие Superset с рабочего компьютера через SSH-туннель
с заглушками адресов. Открытие порта в корпоративную сеть — отдельное решение.

### 5.6. PostgreSQL и Superset

PostgreSQL:
- необходимые базы, схемы, роли и права — без реальных логинов;
- расширения, кодировка, часовой пояс;
- инициализация пустого хранилища и поведение повторного запуска;
- разделение административной роли и подключения Superset для чтения.
  Проверить права роли POSTGRES_USER, не считать её только владельцем БД.

Superset:
- используемые конфигурации и зависимости, драйвер PostgreSQL;
- служебная БД, кэш, workers и планировщик: назначение и необходимость;
- миграции, создание администратора и инициализация ролей;
- что выполняет init-контейнер при каждом запуске;
- безопасный шаблон подключения к учебной БД;
- политики перезапуска и проверки готовности сервисов.

Не объявлять установленным драйвер или настроенной функцию только
потому, что она обычно присутствует в выбранном образе.

### 5.7. Зависимости от Ubuntu

Описать необходимые пакеты, способ установки Docker/Compose, источник
пакетов и требования к сети. Перед подготовкой команд установки проверить
актуальную официальную документацию для целевой Ubuntu.

Отделить обязательные действия от домашних особенностей:
fstab, отдельный раздел данных, перенос Docker data-root,
systemd-зависимость от монтирования, dual boot.
На рабочей ВМ отдельный раздел не требуется.
Не копировать UUID, домашнюю разметку и личные пути.

Описать вариант работы с Docker через sudo или группу docker;
отметить высокий уровень доступа группы docker.
Не менять права автоматически и не использовать chmod 777.

## 6. Выходные файлы

Ориентировочное размещение; сохранить реальные имена и зависимости,
если переименование осложняет перенос:

- infrastructure/README.md — проверяемая инструкция развёртывания;
- infrastructure/postgres/ — Compose и необходимые файлы PostgreSQL;
- infrastructure/superset/ — Compose и все необходимые зависимости
  либо механизм получения зафиксированных исходников;
- .env.example рядом с соответствующим Compose или другой явно
  документированный вариант — выбрать одну согласованную схему;
- technical/home-stand.md — обновлённое фактическое описание;
- docs/status.md — готовность комплекта, проверки, препятствия, следующий шаг;
- docs/decisions.md — только действительно принятые существенные решения.

Обновить .gitignore при необходимости. Маски не защищают уже
отслеживаемые файлы — проверить состав передаваемых изменений.
Рабочие конфигурации не дублировать в папке этапа.
Этот файл задачи дополнить итогом и ссылками на результаты.

## 7. Содержание инструкции развёртывания

Инструкция должна быть выполнима после клонирования на другой Ubuntu:
1. Требования и предварительные проверки.
2. Подготовка каталогов, прав и локальных настроек.
3. Получение зафиксированных зависимостей.
4. Установка компонентов по согласованию с пользователем.
5. Создание новых секретов пользователем.
6. Последовательность первоначального запуска и ожидание готовности.
7. Подключение Superset к учебной БД.
8. Проверка синтетической таблицы и простого графика.
9. Остановка, повторный запуск и сохранность данных.
10. Политики автозапуска и порядок проверки после перезагрузки.
11. Минимальный порядок резервного копирования и восстановления:
    учебная БД, метаданные Superset и необходимые секреты; без передачи
    копий агенту. Отметить, если восстановление ещё не проверялось.
12. Типовые ошибки и безопасная диагностика без вывода секретов.

У каждой команды указывать место исполнения, предпосылки и ожидаемый
результат. Потенциально разрушительные команды вынести в отдельный раздел
с последствиями; не включать их в обычный сценарий перезапуска.

## 8. Проверки и критерии приёмки

Для каждой проверки записать дату, окружение, способ и результат.
Различать «выполнено», «по старым записям», «не проверено» и «не применимо».

- [ ] Версии и состав сервисов сверены с домашней машиной.
- [ ] Все конфигурационные зависимости учтены; скрытых ручных шагов нет.
- [ ] Переменные описаны; действующих секретов и данных в комплекте нет.
- [ ] Конфигурация проверена без раскрытия подставленных секретов.
- [ ] Сети, mounts, права и restart-политики подтверждены.
- [ ] Известен способ подключения Superset к учебной БД; нерешённые
      проблемы исходного стенда явно перечислены.
- [ ] Подготовлены проверки подключения, синтетического графика
      и сохранности состояния.
- [ ] Инструкция различает первый запуск и последующие запуски.
- [ ] Перезапуск, перезагрузка и восстановление, если не выполнялись,
      явно отмечены как непроверенные.
- [ ] Итог передан через файлы репозитория, без зависимости от истории чата.

Статус «комплект подготовлен» не означает «переносимость подтверждена».
Окончательная проверка переносимости — развёртывание на рабочей ВМ
с новыми секретами и успешное прохождение проверок.
Изолированный пробный запуск дома допустим только после согласования:
с отдельными именами проектов, портами и хранилищами.

## 9. Итог для передачи Codex

В конце работы кратко указать:
- какие файлы подготовлены;
- что фактически проверено;
- что требует выполнения пользователем;
- какие вопросы препятствуют развёртыванию;
- следующую конкретную задачу.

Не расширять задачу до DWH, Kubernetes, разработки метрик
или полноценного CI/CD.

# Проблема доступа к Superset: диагностика Docker и KESL

> Статус: актуален
> Обновлено: 2026-10-30 18:56 MSK
> Ответственный: Codex

## 1. Что установили

На рабочей Ubuntu 26.04.1 LTS, архитектура amd64:
- Docker Engine и CLI 29.9.2;
- Docker Compose 5.6.1;
- containerd 2.4.2 и Buildx 0.38.1.

Docker активен, автозапуск включён, hello-world успешно скачан и выполнен.
Используется sudo; группы пользователя не менялись.

Подготовлены общие конфигурации в [infrastructure](../../infrastructure/README.md)
и рабочие копии в ~/bi-stand/. Пользователь задал локальные секреты;
их значения агенту не передавались.

Развёрнуты:
- учебный PostgreSQL из postgres:17; фактическая версия 17.11,
  контейнер bi-postgres, named volume postgres_study_data;
- Superset из apache/superset:3.1.1;
- служебная PostgreSQL Superset из postgres:15;
- Redis из redis:7;
- одноразовая инициализация и фоновые обработчики Superset.

Учебная база study запущена и healthy. Создана роль чтения superset_ro:
пользователь подтвердил парольный вход по TCP и результат запроса
current_user / current_database. Позднее через SET ROLE superset_ro
подтверждено чтение двух строк public.avalon_permissions_demo.
has_table_privilege вернул SELECT=t, INSERT=f, UPDATE=f, DELETE=f.
Таблица создана административной ролью после настройки default privileges:
права по умолчанию для неё сработали. Это не аудит всех прав роли.

superset_init завершился с кодом 0. superset_app, superset_db,
superset_cache и superset_worker показали healthy;
superset_worker_beat работает без отдельной проверки здоровья.

## 2. Что хотели сделать

Развернуть рабочий BI-стенд, затем:
1. Открыть Superset с Windows через SSH-перенаправление порта в VS Code.
2. Подключить Superset к учебной PostgreSQL.
3. Создать синтетическую таблицу и тестовый график.
4. Проверить сохранность состояния после перезапуска.

Сеть bi-net соединяет Superset и учебную базу.
Сеть superset_default используется служебными компонентами Superset.
Веб-порт опубликован только на 127.0.0.1:8088 хоста;
порт учебной базы — на 127.0.0.1:5432.
Прямой доступ из корпоративной сети не настраивался.

## 3. С какой проблемой столкнулись

Браузер Windows по localhost:8088 через перенаправление VS Code
зависает на загрузке страницы.

Проверка с самой Ubuntu:
- localhost:8088/health — тайм-аут без HTTP-ответа;
- повтор без HTTP-прокси через curl --noproxy '*' — тот же результат;
- прямое обращение к обоим IP веб-контейнера — тайм-аут.

При этом внутри контейнера:
docker exec superset_app curl ... http://127.0.0.1:8088/health
возвращает HTTP 200 и OK.

Вывод: приложение работает внутри контейнера, но доступ с хоста
нарушен. Наличие SSH-туннеля само по себе эту проблему не решает.

## 4. Что установили диагностикой

Все результаты ниже получены из вывода команд, выполненных пользователем
на рабочей ВМ 2026-10-30. Агент не менял системные настройки самостоятельно.

### Сети и маршруты

На момент диагностики веб-контейнер имел:
- bi-net: 172.18.0.5, мост br-63355136888b;
- superset_default: 172.19.0.6, мост br-4ed352a659db.

Оба моста UP. Обычные маршруты к IP контейнера направлены через
соответствующие мосты. Для 172.19.0.6 определён MAC-адрес;
состояние соседства STALE само по себе не является ошибкой.

IPv4 forwarding включён: net.ipv4.ip_forward = 1.
rp_filter для all и моста superset_default равен 2;
эту настройку не меняли.

**Важно:** адреса и имена мостов — диагностический снимок.
После пересоздания контейнеров или сетей они могут измениться.

### UFW и временное исключение

UFW активен. Есть исходящий запрет на 172.16.0.0/12,
в который входят обе Docker-подсети.

Пользователь добавил узкое разрешение исходящего TCP:
через br-4ed352a659db к 172.19.0.6, порт 8088.
Первоначально оно стояло после запрета; затем пользователь удалил
это позднее правило и вставил разрешение перед запретом.
По последнему показанному списку разрешение находилось на позиции 6.

Счётчик ACCEPT этого исключения сработал, но доступ не восстановился.
Значит, одного изменения порядка UFW оказалось недостаточно.

**Открытый вопрос:** после исправления совместимости администратору
нужно определить судьбу временного исключения. Не оставлять
привязку к динамическому IP как недокументированное постоянное решение.

### Наблюдение пакетов

tcpdump на мосту superset_default во время прямого curl показал:
- SYN от хоста к 172.19.0.6:8088;
- SYN-ACK от контейнера к хосту.

curl при этом не установил соединение и завершился по тайм-ауту.
Это подтверждает выход запроса на мост и наличие ответа контейнера.
Фильтр захвата выбирал SYN/RST, поэтому сам по себе не показывал все ACK;
вывод о незавершённом подключении опирается также на результат curl.

Журнал UFW не содержал записей о блокировке данного IP в показанном
интервале. Это не доказывает отсутствие блокировки на других этапах.

### Метки KESL и отбрасывание Docker

В mangle/OUTPUT есть переход в kesl_output.
В этой цепочке TCP-трафик к порту 8088 получает метку 0x100;
показанные счётчики правила увеличивались.

KESL также использует NFQUEUE и TPROXY. Само наличие этих целей
не означает блокировку. У показанного правила NFQUEUE в
filter/kesl_input был счётчик 0.

В raw/PREROUTING обнаружено DROP-правило:
отбрасывать пакеты к 172.19.0.6, если входящий интерфейс —
не br-4ed352a659db.

Контрольный тест:
1. До прямого curl счётчик этого DROP: 14 пакетов / 840 байт.
2. curl к 172.19.0.6:8088/health завершился по тайм-ауту.
3. После запроса счётчик DROP: 21 пакет / 1260 байт.
4. Команда ip route get 172.19.0.6 mark 0x100 показала:
   local 172.19.0.6 dev lo table 101 ... mark 0x100.

## 5. К какому решению пришли

Передать диагностику администратору рабочей ВМ или специалисту,
управляющему Kaspersky Endpoint Security for Linux (KESL).
Если ответственный неизвестен — обратиться к сотруднику, выдавшему ВМ.

Попросить проверить и настроить совместимость обработки локального
Docker-трафика с политикой KESL и firewall, сохранив корпоративную защиту.
Конкретный способ исправления должен выбрать ответственный администратор
после проверки конфигурации продукта.

Не отключать KESL/UFW, не очищать iptables и не удалять защитные
DROP-правила Docker как способ обхода проблемы.

## 6. Почему выбрали это решение

Совокупность наблюдений указывает на конфликт перехвата/маршрутизации
трафика KESL с защитными правилами Docker:
- Superset отвечает внутри контейнера;
- обычная маршрутизация и мосты работают на уровне показанных проверок;
- для используемой KESL метки маршрут меняется на локальную доставку через lo;
- во время контрольного запроса растёт соответствующий счётчик DROP;
- узкого разрешения UFW недостаточно.

**Предположение:** конкретная внутренняя настройка KESL, запускающая
этот механизм, и полный путь каждого отброшенного пакета ещё не
подтверждены трассировкой. Не утверждаем, что KESL намеренно блокирует
Superset по политике: возможен конфликт механизмов обработки трафика.

Исправление относится к системной защите ВМ, а не к SQL или настройке
дашборда. Изменения наугад могут ослабить защиту или нарушить другие сервисы.

> На Ubuntu с Docker развёрнут Superset 3.1.1. Внутри контейнера

> KESL помечает исходящий TCP/8088 значением 0x100.

> При запросе к IP контейнера счётчик DROP в raw/PREROUTING
> с условием входа не через Docker-мост вырос с 14 до 21.
> Узкое разрешение UFW перед общим запретом не решило проблему.
> Просьба проверить совместимость KESL и Docker и настроить
> разрешённый доступ хоста к веб-сервису без отключения защиты.

Полные корпоративные правила, журналы и секреты в этот документ не включены.

## 8. На чём остановились и как продолжить

- Шаги 1–5 выполнены; чтение синтетической таблицы и отсутствие
  прав INSERT/UPDATE/DELETE для неё проверены.
- Шаг 6 выполнен в части запуска сервисов и успешной инициализации.
- Доступ хоста к веб-интерфейсу требует исправления; этап целиком
  не считается завершённым.
- Подключение Superset к study, график и проверка сохранности не выполнены.
- Смена стандартного пароля администратора Superset ещё не подтверждена.
  До её выполнения не открывать сервис в корпоративную сеть.

После изменения настроек администратором:
1. Уточнить, какие изменения внесены, и документировать согласованную часть.
2. Проверить актуальные адреса и публикацию порта.
3. С Ubuntu проверить /health через 127.0.0.1:8088 без прокси:
   ожидаются HTTP 200 и OK.
4. Проверить страницу через SSH-туннель и сменить пароль администратора.
5. Продолжить подключение учебной БД и график на синтетических данных.
6. Позже проверить перезапуск и резервное восстановление.

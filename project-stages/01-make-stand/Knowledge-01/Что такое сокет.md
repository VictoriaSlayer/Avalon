## Сокеты: как программы обмениваются данными

### Что такое сокет

**Сокет — объект, которым управляет ядро операционной системы,
через который приложение отправляет и получает данные.**

Условно его можно представить как объект в памяти ядра. Он содержит
не только параметры подключения, но и состояние, ссылки на буферы
и другую информацию, необходимую для обмена данными.

Приложение обращается к сокету через файловый дескриптор —
числовой идентификатор открытого ресурса в процессе.
Через системные вызовы приложение просит ОС создать сокет,
подключиться, отправить или прочитать данные.

**Важно:** IP-адрес и порт — адрес сетевого сокета, а не полное
описание самого объекта. Наличие сокета ещё не означает,
что соединение установлено.

### Пример: DBeaver подключается к PostgreSQL

**Пример — синтетические данные:** адреса и клиентский порт ниже
служат для объяснения. Для простоты обе программы работают
непосредственно на одной Ubuntu, без Docker и SSH-туннеля.

#### Шаг 1. PostgreSQL ожидает подключения

PostgreSQL создаёт TCP-сокет, привязывает его к адресу
`127.0.0.1:5432` и переводит в режим ожидания подключений.

- `127.0.0.1` — loopback-адрес: обращение к этой же машине.
- `5432` — порт, выбранный для PostgreSQL.
- TCP — протокол, обеспечивающий упорядоченную передачу потока байтов.

Такой сокет называется **слушающим**. Он ещё не обслуживает конкретный
SQL-запрос: через него сервер принимает новые подключения.

#### Шаг 2. DBeaver создаёт свою сторону соединения

Пользователь задаёт сервер `127.0.0.1` и порт `5432`.
DBeaver создаёт собственный сокет и инициирует подключение.
ОС обычно сама выбирает свободный временный клиентский порт,
например `52014`.

```text
DBeaver                                  PostgreSQL
127.0.0.1:52014 ─── TCP-соединение ─── 127.0.0.1:5432
```

Одинаковый IP здесь означает, что обе программы находятся
на одной машине; порты у них разные.
На разных машинах IP-адреса сторон обычно различаются.

#### Шаг 3. PostgreSQL принимает соединение

На стороне PostgreSQL создаётся отдельный сокет принятого соединения.
Исходный слушающий сокет остаётся открытым для новых клиентов.

```text
PostgreSQL
├── Слушающий сокет :5432 — принимает новые подключения
├── Сокет соединения с клиентом :52014
└── Сокет соединения с другим клиентом :52015
```

Несколько клиентов могут одновременно подключаться к порту `5432`.
TCP-соединения различаются сочетанием локального IP и порта
с удалённым IP и портом.

Одно приложение может создавать несколько подключений:
один процесс DBeaver не обязательно означает ровно один сокет.

#### Шаг 4. Передача запроса и результата

После установления TCP-соединения клиент и сервер выполняют
обмен по протоколу PostgreSQL, включая аутентификацию.
Затем пользователь запускает запрос:

```sql
SELECT 1;
```

DBeaver кодирует запрос в сообщения протокола PostgreSQL
и отправляет через клиентский сокет. ОС передаёт поток байтов.
PostgreSQL получает сообщения через серверный сокет,
выполняет запрос и отправляет результат обратно.

```text
DBeaver → сокет → TCP → сокет → PostgreSQL
        запрос SELECT 1

DBeaver ← сокет ← TCP ← сокет ← PostgreSQL
        результат 1
```

SQL понимает PostgreSQL. Сокеты и сетевой стек обеспечивают
передачу данных; они не исполняют SQL.

### Адрес, сокет и соединение: различия

| Понятие | Значение | Пример |
|---|---|---|
| IP-адрес | Сетевой адрес | `127.0.0.1` |
| Порт | Номер для адресации сервиса в рамках транспортного протокола | TCP-порт `5432` |
| IP + порт | Адрес конечной точки | `127.0.0.1:5432` |
| Сокет | Объект ОС для обмена данными | Слушающий сокет PostgreSQL |
| TCP-соединение | Связь между двумя конечными точками | Клиент `:52014` ↔ сервер `:5432` |

### Проверка слушающих сокетов: ss

**Назначение для проекта:** перед запуском PostgreSQL и Superset проверить,
не прослушивает ли другой сервис TCP-порты 5432 и 8088.
Если нужный адрес и порт уже заняты, публикация порта контейнера может
завершиться ошибкой. Тогда выясняем, какой сервис их использует,
и выбираем другой внешний порт либо согласуем освобождение текущего.
Команда только читает сведения о сокетах: ничего не останавливает,
не открывает порты и не меняет сетевые настройки.

```bash
ss -ltn '( sport = :5432 or sport = :8088 )'
```

- `ss` — показывает сведения о сокетах.
- `-l` — только слушающие.
- `-t` — только TCP.
- `-n` — адреса и порты числами, без преобразования в имена.
- `sport` — локальный порт в данном фильтре.
- `or` — выбрать порт 5432 или 8088.

Колонки вывода для слушающих TCP-сокетов:

| Колонка | Значение |
|---|---|
| `State` | Состояние; ожидаем `LISTEN` |
| `Recv-Q` | Число установленных соединений, ожидающих принятия приложением |
| `Send-Q` | Предел очереди ожидающих принятия соединений |
| `Local Address:Port` | Локальный адрес и порт |
| `Peer Address:Port` | Другая сторона; у слушающего сокета обычно подстановочный адрес |

Если видны только заголовки, в момент проверки подходящих
слушающих TCP-сокетов не обнаружено.
Это не проверяет доступность порта из другой сети и не гарантирует,
что порт останется свободен до запуска сервиса.

**Важно:** при публикации портов контейнеров Docker сетевой доступ
может обеспечиваться правилами перенаправления без отдельного
слушающего сокета на хосте. Поэтому после запуска контейнеров
проверяем также публикации Docker и фактическое подключение.

### Не все сокеты используют IP и TCP

- UDP-сокеты передают датаграммы и не требуют TCP-соединения.
- Unix domain sockets обеспечивают локальный обмен между процессами;
  могут иметь адрес в виде пути к файлу, без IP и сетевого порта.

В нашем стенде нужно различать Ubuntu-хост и контейнеры:
`127.0.0.1` внутри контейнера относится к его собственному
сетевому окружению. Адрес подключения выбирается с учётом
Docker-сети, публикации портов и SSH-туннеля.

**Проверено:** пользователь передал вывод `ss` только с заголовками
при проверке портов 5432 и 8088 на рабочей ВМ 2026-10-30.
Схема соединения выше — поясняющий пример, не результат запуска стенда.

## Почему конфигурации разделены между infrastructure и bi-stand

Это организационное решение проекта, а не требование Docker.

| Каталог | Назначение |
|---|---|
| `~/Avalon/infrastructure/` | Эталонные Compose-конфигурации, инструкции и шаблоны .env.example, хранящиеся в Git |
| `~/bi-stand/` | Рабочие копии конфигураций конкретного стенда, исходники Superset и локальные .env с секретами |

Compose использует выбранные файлы независимо от названия каталога.
Сам по себе каталог `bi-stand` не делает сервис промышленным:
это место фактического запуска нашего MVP.

Разделение помогает хранить общий комплект без секретов в репозитории,
а настройки конкретной машины — отдельно.
Однако оно не создаёт автоматическую синхронизацию:
изменение файлов в Avalon не меняет их рабочие копии и контейнеры.

### Порядок изменения конфигураций

1. Общее изменение сначала внести в `infrastructure/`.
2. Перенести его в соответствующую рабочую копию в `bi-stand/`.
3. Проверить конфигурацию и применить изменение к сервисам
   в рамках согласованной задачи.
4. Зафиксировать фактический результат в документации.

Если исправление сначала сделано в рабочей копии, перенести
полезную общую часть обратно в `infrastructure/`.
Не копировать локальные настройки целиком без проверки.

**Ограничение:** пароли и ключи из настоящих .env в Git не переносить.
Для новой переменной добавлять в .env.example имя, описание
и безопасную заглушку. Особенности конкретной машины не делать
общими настройками автоматически.

Перед копированием проверить наличие существующих файлов:
обычный `cp` может перезаписать конфигурацию или .env.

Альтернатива — запускать Compose непосредственно из репозитория,
используя отдельные локальные файлы секретов.
Для текущего стенда выбрано разделение; его цена —
необходимость поддерживать копии согласованными.
